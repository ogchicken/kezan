# Opened items, reload and zone research, 27 November 2026

Desk research for four questions the session design raises: how disenchanting reports its results on Forever, how an addon tells which item was opened when an item turns into loot ([ADR 0004](../docs/adr/0004-a-session-counts-loot-when-it-arrives.md), "Opened items"), what `PLAYER_ENTERING_WORLD` carries, and which call records a session's zone. It builds on [2026-11-27-loot-and-money-events.md](2026-11-27-loot-and-money-events.md) and does not repeat it.

On sources: as in that note, the firmest source is Blizzard's generated API documentation and UI code for the Forever client, in the `forever` branch of [Gethe/wow-ui-source](https://github.com/Gethe/wow-ui-source/tree/forever) at build 1.60.1 (71139). Undocumented globals were checked in [Ketho/BlizzardInterfaceResources](https://github.com/Ketho/BlizzardInterfaceResources/tree/forever) (`forever` branch, 70938). Blizzard's code shows what the client does with an event; it cannot show what the server sends, and how disenchanting delivers its results is decided by the server. For that, this note relies on Forever addons, and keeps three kinds of evidence apart: what **the docs declare**, what **an addon does** (its code, which shows a design, not a fact), and what **someone observed** in game (an author's own recorded trace or measurement). Code comments that guess are not counted as observations. Items marked *unverified* need the in-game check at the end. No addon code is copied here.

Permalinks use these commits: wow-ui-source `forever` [`d9c22e3`](https://github.com/Gethe/wow-ui-source/commit/d9c22e32cb240afb82bb2ecefbb78ef935333f59); BlizzardInterfaceResources `forever` [`e230342`](https://github.com/Ketho/BlizzardInterfaceResources/commit/e230342a476eb4ef484ba7b34adc0da6ecc6acc1). Addon commits are in each link. All the addons cited declare `## Interface: 16001` unless stated.

The Forever AddOns folder on this machine holds Auctionator, BigWigs, LittleWigs, EllesmereUI (with EllesmereUIBags and EllesmereUIQoL), GatherMate2, Polestar, RareScanner, DeleteCheapestItem, ZygorGuidesViewerForever, BugSack, Simulationcraft and others. None of them tracks disenchanting results. Auctionator only prices; EllesmereUIBags has a Disenchant quick action (a secure spell button, section 2).

## 1. Disenchanting on Forever

### What Blizzard's code shows

- The client's loot window is the Mainline one, loaded on Forever through `[Family]\LootFrame.lua` ([Blizzard_UIPanels_Game.toc#L127](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_UIPanels_Game/Blizzard_UIPanels_Game.toc#L127)). On `LOOT_OPENED(isAutoLoot, acquiredFromItem)` it plays the container sound when the second argument is true, the reel sound for fishing, and nothing special for anything else ([LootFrame.lua#L127-L146](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/LootFrame.lua#L127-L146)). It has no disenchant-specific branch.
- The docs declare `LOOT_OPENED(autoLoot, isFromItem)` and `LOOT_READY(autoloot)`, neither with a secret predicate ([LootDocumentation.lua#L218-L237](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/LootDocumentation.lua#L218-L237)). Only `LOOT_OPENED` carries `isFromItem`.
- The only other disenchant references in Forever's UI code are the group-loot "Disenchant" roll and `C_SpellBook.ContainsAnyDisenchantSpell` ("Returns true if player knows any Disenchant spells", [SpellBookDocumentation.lua#L33-L35](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/SpellBookDocumentation.lua#L33-L35)). There is no disenchant chat string: the results can only arrive as one of the general loot strings, `LOOT_ITEM_SELF` "You receive loot: %s" or `LOOT_ITEM_PUSHED_SELF` "You receive item: %s" ([enUS.lua#L13873-L13878](https://github.com/Ketho/BlizzardInterfaceResources/blob/e230342a476eb4ef484ba7b34adc0da6ecc6acc1/Resources/GlobalStrings/enUS.lua#L13873-L13878)).
- So the client code cannot settle the question. It needs addon evidence or an in-game check.

### What Forever addons observed

- **BagSmith** (Shweep8/bagsmith, 1.11.0) records two traces from the game in its code comments, each written as a finding from the author's own run, not a guess:
  - 15 November, auto-loot on and off: "a disenchant's window says "Item-...", a creature's "Creature-..." with a coin slot". A later debug line from the game shows the loot source GUID equal to the disenchanted item's GUID: "loot slot 1's source is the disenchanted item (Item-6796-0-40000000257B6C17; item Item-6796-0-40000000257B6C17)". [Disenchant.lua#L1274-L1289](https://github.com/Shweep8/bagsmith/blob/9a3985387fc2bccc119ebe4c7af96d467add7384/BagSmith/Core/Disenchant.lua#L1274-L1289)
  - 27 November, auto-loot on and off: "a disenchant's loot comes from its own loot window and is announced as "You receive loot"; "You receive item" never came." BagSmith now refuses to count a "You receive item" line as a disenchant's. [Disenchant.lua#L456-L470](https://github.com/Shweep8/bagsmith/blob/9a3985387fc2bccc119ebe4c7af96d467add7384/BagSmith/Core/Disenchant.lua#L456-L470)
- **Salvager** (rojosinalma/salvager) books a disenchant only from `LOOT_READY`, reading `GetLootSlotLink` and `GetLootSlotInfo` within 15 seconds of a `UNIT_SPELLCAST_SENT` for 13262 ([Disenchant.lua#L106-L163](https://github.com/rojosinalma/salvager/blob/b613ed0f220f4cdaacb268207b05b630747a308f/Salvager/Disenchant.lua#L106-L163)). Its design notes record measured batches of 36 and 30 disenchants on 26 November, with per-result material counts ([SDD.md#L313-L316](https://github.com/rojosinalma/salvager/blob/b613ed0f220f4cdaacb268207b05b630747a308f/docs/SDD.md#L313-L316), [#L337](https://github.com/rojosinalma/salvager/blob/b613ed0f220f4cdaacb268207b05b630747a308f/docs/SDD.md#L337)). Since the loot window is its only path, those records imply a loot window with readable slots after each disenchant. Indirect, but from real play.
- **Shatter** (Spotnick2/Shatter) lists the order of `UNIT_SPELLCAST_SUCCEEDED`, `LOOT_READY`, `LOOT_OPENED` with `isFromItem`, `LOOT_CLOSED` and `BAG_UPDATE_DELAYED` as an open question, "not measured" ([FOREVER-PROBE.md#L46](https://github.com/Spotnick2/Shatter/blob/62465e8829fcd632461b95a9d5008d09f746ed9a/docs/FOREVER-PROBE.md#L46)). Its tests feed `isFromItem true` as a mock, which is not an observation.
- Most other Forever disenchant addons read the loot window on `LOOT_READY` or `LOOT_OPENED` after a 13262 cast: Krool World Forever, DisenchantValue, EnchantPilot, Tradebook, Everloot, ForeverTweaks. Doudster's DoudProfessions and Skillwright parse `CHAT_MSG_LOOT` and accept both the "loot" and "item" forms. These show designs, not observations.

### `isFromItem` for disenchanting

- No source says what `isFromItem` is when disenchanting. *Unverified.*
- GoldWise (flightpathlabs/GoldWise) treats a loot window as "from the bags" when `isFromItem` is true, or when 13262 succeeded within its cast window, or when `GetLootSourceInfo(1)` starts with `Item-` ([Activity.lua#L724-L737](https://github.com/flightpathlabs/GoldWise/blob/62171f7ad808bdc5d687f528e82e838ab8a370ae/Profile/Activity.lua#L724-L737), [#L788-L800](https://github.com/flightpathlabs/GoldWise/blob/62171f7ad808bdc5d687f528e82e838ab8a370ae/Profile/Activity.lua#L788-L800)). Its comment "though the game didn't say so" is a hedge, not an observation.
- `isFromItem` is only on `LOOT_OPENED`, and `LOOT_OPENED` may not fire at all with fast auto-loot: ForeverPlusPlus observed that mining with Fast Loot gave no `LOOT_OPENED`, so it reads loot at `LOOT_READY` (build 70862, [forever-api.md#L405](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/6b98426f7b8132bf0dfb3e8620484ae9621e0054/docs/forever-api.md#L405)). So `isFromItem` cannot be the only test for an item-sourced window.

### Classic Era and Retail

- No Blizzard statement on either was found. Addon evidence only:
- TradeSkillMaster's Destroying module (v4.14.78, Retail TOC `## Interface: 120105`, the same module ships for Classic) waits for `UNIT_SPELLCAST_SUCCEEDED` for 13262, then a `LOOT_READY` with `GetNumLootItems() > 0`, reads the slots, then waits for `LOOT_CLOSED` and `BAG_UPDATE_DELAYED` ([Core.lua#L316-L345](https://github.com/luhao007/WoW-Addons/blob/b88022cf5c865507a3a8dd3a204218f0c6796f27/AddOns/TradeSkillMaster/Core/Service/Destroying/Core.lua#L316-L345), a third-party mirror). On Retail it also hooks `C_TradeSkillUI` salvage crafts and reads `TRADE_SKILL_ITEM_CRAFTED_RESULT` ([#L142-L149](https://github.com/luhao007/WoW-Addons/blob/b88022cf5c865507a3a8dd3a204218f0c6796f27/AddOns/TradeSkillMaster/Core/Service/Destroying/Core.lua#L142-L149)). EllesmereUIBags says "Milling and Prospecting are profession salvage recipes, not item-targeted spells" (installed copy, 9.9.6, `EllesmereUIBags_QuickActions.lua` line 20). So on Retail, Disenchant itself still uses a loot window and the salvage recipes push their results; on Classic Era, Disenchant uses a loot window.
- Forever's observed behaviour (BagSmith, Salvager) matches the Classic and Retail Disenchant spell: a loot window, "You receive loot". This is the server's behaviour, not something the Mainline client code changes.

### Prospecting and milling

- No source shows that Prospecting (31252) or Milling (51005) exist on Forever, a level 60 game built on Classic's professions. GoldWise lists them "should the client have them". *Unverified;* treat them as absent.

### Verdict

Disenchanting on Forever opens a loot window. Its slots are readable on `LOOT_READY`, each slot's `GetLootSourceInfo` names the disenchanted item's own `Item-` GUID, and taking the loot gives "You receive loot" lines (`LOOT_ITEM_SELF*`), never "You receive item". This rests on one addon author's recorded traces (BagSmith, 15 and 27 November) and on Salvager's measured batches; no Blizzard source states it. So Kezan can count disenchant results through the same "You receive loot" path as other loot, as ADR 0004 assumes. Whether `isFromItem` is true for a disenchant is unknown, and `LOOT_OPENED` can be skipped with fast loot, so the opened item must be found another way (section 2).

## 2. Which item was opened

ADR 0004 needs the opened item's **item ID**, so that one unit of it can leave the session. It does not need the item instance: a stack of clams is one item with one GUID, and new clams merge into it, so a GUID cannot say whether a unit was held before the session anyway. Counting by item ID is enough.

### Details

- **Loot source GUID.** The wiki says `GetLootSourceInfo` returns `guid, quantity` pairs and "Item guids for containers like lockboxes" ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetLootSourceInfo)). On Forever, BagSmith observed the disenchanted item's own GUID there (section 1). For clams and lockboxes on Forever it is *unverified*. EverlookDB, GoldWise and Everloot treat any `Item-` source as "opened from the bags" ([EverlookDB.lua#L805-L818](https://github.com/quikmn/EverlookDB/blob/73b27743d70369cc88603cb2e6fa5b8a24f55db8/EverlookDB.lua#L805-L818), [openworld.lua#L31-L36](https://github.com/Everloot/everloot/blob/6c28cb2ee859540e5c8c157fc7453300c65a1199/addon/modules/openworld.lua#L31-L36)). ForeverTweaks still calls the `Item-` GUID "Mainline's; unverified on Forever" ([ItemDisenchant.lua#L95-L98](https://github.com/dcizov/forever/blob/3a4aa48f838f10030a0c3d7027a007f9a78689fc/ForeverTweaks/Modules/Tooltips/ItemDisenchant.lua#L95-L98)); that predates BagSmith's trace.
- **GUID to item ID.** The GUID does not hold the item ID ([openworld.lua#L393-L400](https://github.com/Everloot/everloot/blob/6c28cb2ee859540e5c8c157fc7453300c65a1199/addon/modules/openworld.lua#L393-L400)). Everloot asks `C_Item.GetItemIDByGUID`; Krool asks `C_Item.GetItemLinkByGUID` at loot time ([Disenchant.lua#L301-L335](https://github.com/Krool/KroolWorldForever/blob/59e6055096f615c260262397e5fee416bb0f0c4b/KroolWorldForever/Features/Disenchant/Disenchant.lua#L301-L335)); BagSmith and Salvager instead read the target's GUID with `C_Item.GetItemGUID` before the loot and compare. A bag map of GUID to item ID, rebuilt on `BAG_UPDATE_DELAYED`, answers even after the item is gone.
- **The hook.** Forever's default bags call `C_Container.UseContainerItem` on a right-click ([ContainerFrame.lua#L1611](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/ContainerFrame.lua#L1611)) and on a left-click while a spell waits for an item target, which is how Disenchant picks its item ([#L1503-L1510](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_UIPanels_Game/Mainline/ContainerFrame.lua#L1503-L1510)). The Camelot override file changes neither ([Camelot/ContainerFrame.lua](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_UIPanels_Game/Camelot/ContainerFrame.lua)). Secure buttons with `target-bag`/`target-slot` call it too ([SecureTemplates.lua#L769-L775](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_FrameXML/SecureTemplates.lua#L769-L775)), and so does `/use <bag> <slot>`; `/use <name>` goes through `C_Item.UseItemByName` instead ([ChatFrameUtil.lua#L1228-L1236](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_ChatFrameBase/Shared/ChatFrameUtil.lua#L1228-L1236)). EllesmereUIBags builds its slots from Blizzard's `ContainerFrameItemButtonTemplate` (installed copy), so it takes the same path.
  - Observed: ForeverPlusPlus's `hooksecurefunc` on `C_Container.UseContainerItem` ran inside the player's own right-click on a Coarse Weightstone (it then hit `ADDON_ACTION_FORBIDDEN` for calling a protected function from the hook; build 70338, [forever-api.md#L345](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/6b98426f7b8132bf0dfb3e8620484ae9621e0054/docs/forever-api.md#L345)). So the hook fires on Forever. The lesson for Kezan: the hook must only record, never call anything protected.
  - EverlookDB says "Forever's bag buttons don't pass through UseContainerItem, so the hooks below rarely see a bag click" and falls back on `ITEM_LOCKED` and bag diffs ([EverlookDB.lua#L599-L606](https://github.com/quikmn/EverlookDB/blob/73b27743d70369cc88603cb2e6fa5b8a24f55db8/EverlookDB.lua#L599-L606)). Forever's own bag code contradicts this for the default bags, and the comment gives no build or trace. Likely the author's bag addon bypassed it; *unverified*.
- **Spellcast events.** For the player's own casts, the declared predicate does not make them secret: "Guarded APIs and events produce secret values if the unit being queried for cast information is not the player or their pet. Individual spells may be flagged as never or always secret, which takes priority." ([SecretPredicatesDocumentation.lua#L115-L118](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/SecretPredicatesDocumentation.lua#L115-L118)). Whether 13262 is flagged is not public; GoldWise and Krool guard the spell ID with a secret check anyway. Everloot and DisenchantValue read the `SENT` target as the disenchanted item's name and look it up ([openworld.lua#L237-L255](https://github.com/Everloot/everloot/blob/6c28cb2ee859540e5c8c157fc7453300c65a1199/addon/modules/openworld.lua#L237-L255), [Log.lua#L56-L75](https://github.com/quikmn/DisenchantValue/blob/8b5c96bdae87a79f6ca6456e455a91faf5787407/Log.lua#L56-L75)). That the target is the item's name for Disenchant is *unverified*; ForeverPlusPlus observed that for Mining the target is the vein's name ([forever-api.md#L405](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/6b98426f7b8132bf0dfb3e8620484ae9621e0054/docs/forever-api.md#L405)). A name does not tell two items of the same name apart.
- **Locks.** Salvager takes the weapon or armour whose lock changes after a Disenchant `SENT` as the target ("The game locks the item the spell is aimed at", [Disenchant.lua#L120-L135](https://github.com/rojosinalma/salvager/blob/b613ed0f220f4cdaacb268207b05b630747a308f/Salvager/Disenchant.lua#L120-L135)). EverlookDB records every `ITEM_LOCKED` and, when Disenchant begins, takes the item locked in the bags then ([EverlookDB.lua#L1577-L1600](https://github.com/quikmn/EverlookDB/blob/73b27743d70369cc88603cb2e6fa5b8a24f55db8/EverlookDB.lua#L1577-L1600)). ForeverDB combines the hook, the lock and the spell cursor, and notes that "Forever's Combined Backpack path may expose an item-targeting spell cursor without returning the spell ID" ([DisenchantTracker.lua#L35-L39](https://github.com/Imemoth/wow-foreverdb/blob/ddabf52b1983e4e154dc7e148f7ce492da2758ae/addon/ForeverDB/DisenchantTracker.lua#L35-L39)). These are designs; none records a trace.

### Failure modes

- **Auto-loot and fast loot.** The window may open and empty within a frame, and `LOOT_OPENED` may not fire. Read on `LOOT_READY`; `LOOT_READY` and `LOOT_OPENED` both fire for one window when both come, so read once per window (BagSmith, Krool, Salvager all guard this).
- **Stacked clams.** One stack, one GUID. Opening one unit lowers the stack's count; the GUID still resolves while the stack has units left. The last unit's GUID may not resolve after the window empties. *Unverified.*
- **Several quickly.** Only one loot window is open at a time. Whether using a second container while one window is open closes the first or is refused is *unverified*; EllesmereUIQoL's container opener waits for `LOOT_CLOSED` before opening the next, saying an open "while up strands them" (installed copy, `EllesmereUIQoL.lua` line 392). Shatter asks the same question for two quick disenchants (section 1). Matching each window to its source by GUID, not by timing, avoids the problem.
- **Empty windows.** A window with no slots has no source to ask. It has nothing to count either.
- **Dungeons.** Item GUIDs from `GetLootSourceInfo` may turn secret in instances like creature GUIDs. *Unverified;* guard with `issecretvalue`. If it is secret, the contents count and nothing is removed, as ADR 0004 allows.

### Verdict

Use the loot window's own source. On `LOOT_READY`, ask `GetLootSourceInfo` for each slot; a source GUID starting `Item-` marks an opened item. Resolve the GUID to an item ID from a map of bag GUIDs to item IDs that Kezan keeps from `C_Item.GetItemGUID`, refreshed on `BAG_UPDATE_DELAYED`, with `C_Item.GetItemIDByGUID` as a second try. This needs no cast, no hook and no timing, works the same for clams, lockboxes and disenchanting, and survives auto-loot. A read-only `hooksecurefunc` on `C_Container.UseContainerItem` and `UNIT_SPELLCAST_SUCCEEDED` for 13262 are useful as a fallback only, when the source is unreadable. When neither tells the item, count the contents and remove nothing, as ADR 0004 says. That the GUID is an `Item-` GUID is observed for disenchanting only; for clams and lockboxes it is the wiki's statement, *unverified* on Forever.

## 3. `PLAYER_ENTERING_WORLD`, logout and saved variables

- The docs declare `PLAYER_ENTERING_WORLD` with the payload `isInitialLogin` (bool), then `isReloadingUi` (bool), both `Nilable = false`, with no secret predicate and no `ConditionalSecret` field ([SystemDocumentation.lua#L134-L143](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/SystemDocumentation.lua#L134-L143)). The system is `Environment = "All"`.
- The wiki: "Fires when the player logs in, reloads the UI or zones between map instances. Basically whenever the loading screen appears." `isInitialLogin` is "True whenever the character logs in. This includes logging out to character select and then logging in again." The parameters were added in 8.0.1. ([Warcraft Wiki: PLAYER_ENTERING_WORLD](https://warcraft.wiki.gg/wiki/PLAYER_ENTERING_WORLD))
- The same file declares `PLAYER_LEAVING_WORLD`, `PLAYER_LOGIN`, `PLAYER_LOGOUT` and `PLAYER_QUITING`, none with a payload ([SystemDocumentation.lua#L144-L167](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/SystemDocumentation.lua#L144-L167)). `ADDONS_UNLOADING(closingClient)` is declared too ([AddOnsDocumentation.lua#L399-L408](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/AddOnsDocumentation.lua#L399-L408)). All are in Ketho's Forever event list ([Events.lua#L41](https://github.com/Ketho/BlizzardInterfaceResources/blob/e230342a476eb4ef484ba7b34adc0da6ecc6acc1/Resources/Events.lua#L41), [#L1821-L1824](https://github.com/Ketho/BlizzardInterfaceResources/blob/e230342a476eb4ef484ba7b34adc0da6ecc6acc1/Resources/Events.lua#L1821-L1824)).
- When saved variables are written, per the wiki: the client writes them "when you log out, disconnect, quit the game, or reload your user interface (`/reload`)", and `PLAYER_LOGOUT` "fires just before the character logs out, and is the last event before your saved variables are written to disk". They are loaded before the addon's `ADDON_LOADED`. ([Warcraft Wiki: Saving variables between game sessions](https://warcraft.wiki.gg/wiki/Saving_variables_between_game_sessions)). Nothing is written on a crash, by the usual understanding; the page does not say. *Unverified.*
- Observed on Forever: saved variables persist across a full client exit. ForeverPlusPlus saw a load counter grow across sessions (checked 25 September, [forever-api.md#L61](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/6b98426f7b8132bf0dfb3e8620484ae9621e0054/docs/forever-api.md#L61)); Shatter saw its login stamps come back across client restarts on 70959 and 71037 ([forever-api-notes.md#L21-L27](https://github.com/Spotnick2/Shatter/blob/62465e8829fcd632461b95a9d5008d09f746ed9a/docs/forever-api-notes.md#L21-L27)).
- Addons: AnotherLedger handles `PLAYER_ENTERING_WORLD(isInitialLogin, isReloadingUi)` and keeps the session on a reload ([Core.lua#L770-L798](https://github.com/mxhes/AnotherLedger/blob/10a14ae4f0ad8ce477565f008d112b140440f328/AnotherLedger/Core.lua#L770-L798)); GoldPerHour resumes a session when the second argument is true ([GoldPerHour.lua#L897-L909](https://github.com/kejith/GoldPerHour/blob/e157fbf1bb1a89a60c6d8d1e5a845b6e1ddf314b/GoldPerHour.lua#L897-L909)). ForeverPlusPlus calls the login order (`PLAYER_LOGIN`, then `PLAYER_ENTERING_WORLD` with these flags) "the Retail order" and *unverified* on Forever ([forever-api.md#L292](https://github.com/xIGBClutchIx/ForeverPlusPlus/blob/6b98426f7b8132bf0dfb3e8620484ae9621e0054/docs/forever-api.md#L292)).
- Verdict: the payload is `isInitialLogin, isReloadingUi`, in that order, with no secret tags. `PLAYER_LOGOUT` and `PLAYER_LEAVING_WORLD` exist. Saved variables are written on logout, disconnect, quit and `/reload`, after `PLAYER_LOGOUT`; write the session into the saved table as it changes rather than only on `PLAYER_LOGOUT`, so a crash loses little. That the flags arrive as declared is addon evidence, not observed in a trace.

## 4. Recording the zone

- The docs declare `GetZoneText`, `GetRealZoneText([mapID])`, `GetSubZoneText`, `GetMinimapZoneText` and `GetAreaText`, each returning a non-nil `cstring`, in a system with `Environment = "All"` and no predicates ([ZoneScriptDocumentation.lua#L9-L60](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/ZoneScriptDocumentation.lua#L9-L60)). `GetRealZoneText` "Returns the map instance name" ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/API_GetRealZoneText)).
- `GetInstanceInfo()` returns `name, instanceType, difficultyID, difficultyName, maxPlayers, dynamicDifficulty, isDynamic, instanceID, instanceGroupSize, lfgDungeonID, hasWorldTier`, and `IsInInstance()` returns `isInInstance, instanceType`, both with no secret tags ([InstanceDocumentation.lua#L103-L121](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/InstanceDocumentation.lua#L103-L121), [#L170-L178](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/InstanceDocumentation.lua#L170-L178)).
- `C_Map.GetBestMapForUnit(unit)` ("Only works for the player and party members", `uiMapID` nilable) and `C_Map.GetMapInfo(uiMapID)` (`mapID`, `name`, `mapType`, `parentMapID`, `flags`) carry only `SecretArguments = "AllowedWhenUntainted"` ([MapDocumentation.lua#L49-L63](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/MapDocumentation.lua#L49-L63), [#L312-L326](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/MapDocumentation.lua#L312-L326), [#L696-L705](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/MapDocumentation.lua#L696-L705)).
- None of these is tagged secret, in instances or anywhere. Whether `GetBestMapForUnit` returns a map inside Forever's Classic dungeons is *unverified*; Classic dungeons often have no map of their own.
- `ZONE_CHANGED`, `ZONE_CHANGED_INDOORS` and `ZONE_CHANGED_NEW_AREA` are declared, without payloads ([MapDocumentation.lua#L651-L667](https://github.com/Gethe/wow-ui-source/blob/d9c22e32cb240afb82bb2ecefbb78ef935333f59/Interface/AddOns/Blizzard_APIDocumentationGenerated/MapDocumentation.lua#L651-L667)). The wiki: `ZONE_CHANGED_NEW_AREA` "Fires when the player enters a new zone" ([Warcraft Wiki](https://warcraft.wiki.gg/wiki/ZONE_CHANGED_NEW_AREA)). Entering an instance also brings a loading screen and `PLAYER_ENTERING_WORLD`.
- What Forever addons use: `GetRealZoneText` is the most common (14 of the 28 addons read), usually with `GetZoneText` as a fallback. ForeverLootTracker takes `GetInstanceInfo()`'s name when `IsInInstance()`, else `GetRealZoneText`, else `GetZoneText` ([Core.lua#L93-L101](https://github.com/Westfall-Digital/ForeverLootTracker/blob/05276f486637aed24ddeb63cfb60ee7d4703a849/Core.lua#L93-L101)). AnotherLedger does the same and adds the difficulty name ([Core.lua#L104-L121](https://github.com/mxhes/AnotherLedger/blob/10a14ae4f0ad8ce477565f008d112b140440f328/AnotherLedger/Core.lua#L104-L121)). GoldWise prefers `C_Map.GetBestMapForUnit("player")`, walks up past micro maps with `C_Map.GetMapInfo`, and falls back to `GetRealZoneText` ([Activity.lua#L217-L246](https://github.com/flightpathlabs/GoldWise/blob/62171f7ad808bdc5d687f528e82e838ab8a370ae/Profile/Activity.lua#L217-L246)). Time Is Money stores `GetRealZoneText()` with `IsInInstance()`'s type ([Core.lua#L304](https://github.com/RyrinsRealm/Time-Is-Money/blob/591eeecb1f1bcbbc3ac0a547f6a9b5b4b1cc7da0/Core.lua#L304)). GoldWise and ForeverLootTracker wrap the text in a "readable" check; that is defensive, as nothing is tagged.
- Verdict: record `GetRealZoneText()` when the session starts, falling back to `GetZoneText()` when it is empty. It names the open-world zone and, inside an instance, the instance. Store the `uiMapID` from `C_Map.GetBestMapForUnit("player")` beside it if a stable key is wanted, but do not depend on it in dungeons. Listen for `ZONE_CHANGED_NEW_AREA` (and `PLAYER_ENTERING_WORLD`) if the zone is ever to follow the player. All of these are declared on Forever and none is tagged secret.
